# KYUTXO - Bitcoin Metadata Manager

## Overview
KYUTXO is an offline-first desktop application designed for managing Bitcoin address and transaction metadata. Its primary purpose is to help users organize cryptocurrency information, attach relevant files, and manage custom vocabularies, all while prioritizing data privacy. The application operates completely offline and includes a password-based UI locking mechanism. KYUTXO aims to become a comprehensive personal crypto data management solution, with future ambitions including advanced provenance tracking, entity relationship mapping, and compliance reporting. The immediate focus is on efficient blockchain data import and transaction synchronization.

## User Preferences
Preferred communication style: Simple, everyday language.

## System Architecture
KYUTXO features an offline-first architecture built for cross-platform desktop deployment using Electron. The frontend is developed with React 18, TypeScript, and Vite, leveraging `shadcn/ui` and Tailwind CSS for a responsive user interface. State management is handled by TanStack Query and Dexie.js for IndexedDB. A local Express.js backend primarily serves file attachments, with core business logic residing client-side.

**Key Architectural Decisions & Features:**

*   **UI/UX:** Responsive, offline-first interface with streamlined navigation.
*   **Data Model:** Comprehensive records for tracking ownership, wallet names, and metadata.
*   **Security:** Implements a password-based UI lock (hash check only); data is stored as plaintext in IndexedDB. Users requiring data-at-rest protection should utilize OS-level encrypted containers.
*   **Performance:** Utilizes DB-level and cursor-based pagination, indexed lookups (including `inputStringLower` for O(1) case-insensitive record search), and debounced search for efficient data handling. Search pending opacity is configurable per page via `PAGE_SEARCH_PENDING_OPACITY` in `client/src/config/debounce.ts` (defaults to `opacity-60`). Transactions page uses iterative batched scanning to search across the entire database without caps, yielding between batches to keep the UI responsive; search results use virtual scrolling (@tanstack/react-virtual) with on-demand participant data loading for visible items, replacing pagination for smooth scrolling through up to 50,000 matches. Bulk Editor uses database-level filtering with index-optimized queries instead of loading records into memory, and virtual scrolling for both the preview list and confirmation dialog to keep the UI smooth with up to 10,000+ matching records. Quick Tagger uses virtual scrolling for its review table (supporting 1000+ pasted entries) and targeted `inputString` index lookups instead of loading all records. UTXOs page uses virtual scrolling with a flattened row model (address groups + expanded UTXOs) instead of pagination, allowing smooth scrolling through all addresses. Descriptor Import uses targeted `inputString` index lookups.
*   **Offline First & Portability:** Designed for full offline functionality and portable database storage.
*   **Data Management:** Includes features for custom vocabulary management, duplicate detection and merging, and bulk address/descriptor/BIP-329 label importing.
*   **Wallet Data Sync:** Modular system for importing labels and transaction history from various wallet software, including mobile wallets, with duplicate detection.
*   **Transaction Sync System:** Fetches and imports confirmed transactions from blockchain sources for tracked addresses, intelligently matching and creating "Pending Review" records. Features include pause/resume, parallel fetching, caching, batched writes, and prevout resolution.
*   **Privacy & Connectivity:** Supports Tor proxy integration for privacy-enhanced node connectivity and Electrum Protocol for efficient bulk address syncing.
*   **UTXO Tracking:** Offers dual-mode UTXO calculation (Standard/Exact) with outpoint-based matching.
*   **Reporting & Analysis:** Includes a Source of Funds Report, Hop-Point Detection Report, Statement Report, Privacy Audit (on-chain vulnerability scanner), Quantum Risk Scanner, and a Balance Overview.
*   **Visualization:** Features a Bitcoin Flow Visualizer for UTXO provenance tracing and a Network Analysis tool for visualizing Bitcoin address relationships as a force-directed graph.
*   **Workflow Tools:** Provides a Quick Tagger for bulk labeling, Nudgie for unlabeled transaction workflow, a Database Cleanup utility for managing blockchain-discovered records, and a Discovery Tree Dialog.
*   **Metadata & Editing:** Supports transaction classification metadata, a bulk editor for batch modifications, and a metadata conflict resolution system using a `RecordOrigin` system.
*   **Origin Tracking System:** Comprehensive UTXO lineage tracking with `utxoLineage` and `custodySegment` tables, a Lineage Engine, Continuity Proof, Continuity Certificate Report, and Evidence Bundle Export. Partial export bundles are persisted to IndexedDB (`partialExportBundles` table) so they survive page refreshes; the `partialBundleStore.ts` module provides save/load/clear operations keyed by the sorted set of selected segment IDs. The cancel confirmation threshold for lineage builds is configurable via Settings > Lineage Build (stored in `settings.cancelConfirmThreshold`, default 75%).
*   **Privacy Entity List:** The Privacy Audit matches participant addresses against a bundled, in-repo dataset (`client/src/lib/privacy-entity-list.ts`) compiled from public sources (WalletExplorer, GraphSense TagPacks, OFAC SDN). Because these sources change over time and KYUTXO is strictly offline, users can refresh detection via Settings > Privacy Audit Entity List: import an updated JSON snapshot (a bare array, or `{ entries: [...] }`, of `{ address, name, category, sourceNote? }`), which is validated (valid Bitcoin addresses, known categories, no duplicates) and, on success, *replaces* the active list and is persisted to `settings.entityListSnapshot`. The bundled list remains the fallback (restored via "Revert to bundled"), the current list can be exported as an editable template, and the persisted snapshot is re-applied at startup. No network access is ever added. Persistence + validation live in `client/src/lib/data/entity-list-store.ts`.
*   **Adversary View Browser Guard:** The Privacy Audit's Adversary View panel (async `runAdversaryView` fired after the main audit in `client/src/pages/PrivacyAudit.tsx`) is covered by a registered validation step (`adversary-view-browser-check`, `node scripts/check-adversary-view-browser.mjs`). It drives a REAL headless Chromium: creates a fresh vault, seeds two owned address records co-spending as inputs in one transaction (via Vite dynamic imports of the live CRUD singletons), installs a MutationObserver before clicking Run Audit (so the transient `text-adversary-status` loading message is captured even on a fast analysis), runs the audit, and asserts the `container-adversary-view` panel appears, the loading status was observed, the summary stats match the seed exactly (2 exposed / 0 separated / 0 confusion / 0 context merges), the header "1 exposure" badge matches the section badge count, no other category badges render, and the no-XPUB degradation banner shows. Runs fully offline (local IndexedDB only); needs `chromium` on PATH + `playwright-core` and reuses the dev server or spawns one. Note: the adversary result lives only in React state — a page refresh mid-analysis discards it (no persistence yet). Run `node scripts/check-adversary-view-browser.mjs` to verify.
*   **Evidence Storage:** General-purpose document storage for proof-of-ownership and historical records.
*   **Vault Management:** Dedicated UI for viewing and managing multisig vaults.

## Data Layer Conventions
*   **CRUD Layer Guards:** Write operations on the following tables must go through their dedicated CRUD modules (re-exported via `dataFacade.ts`). Direct writes outside the CRUD module are prohibited. This constraint is enforced automatically via a git pre-commit hook and a registered validation step (`crud-guards`). Run `scripts/install-hooks.sh` to reinstall the pre-commit hook after cloning. Database migrations in `database.ts` that use `tx.table(...)` are exempt. Run `node scripts/check-crud-guards.js` to manually verify compliance.
    *   `db.records` → `client/src/lib/data/record-crud.ts`
    *   `db.blockchainTransactions` → `client/src/lib/data/transaction-crud.ts`
    *   `db.transactionParticipants` → `client/src/lib/data/transaction-crud.ts`
    *   `db.utxoLineage` → `client/src/lib/data/lineage-crud.ts`
    *   `db.custodySegments` → `client/src/lib/data/lineage-crud.ts`
    *   `db.evidence` → `client/src/lib/data/evidence-crud.ts`
    *   `db.evidenceAttachments` → `client/src/lib/data/evidence-crud.ts`
    *   `db.lineageSnapshots` → `client/src/lib/data/lineage-crud.ts`
*   **Safe Note Rendering Guard:** Every free-text note surface (record notes, cosigner notes, evidence notes, metadata-source notes, Nudgie notes, Reports/Privacy Audit finding descriptions + remediation text, and source citation notes — including the Settings entity-list conflict diffs) must render through the shared safe link renderer `renderSourceNote` (`client/src/lib/renderSourceNote.tsx`), which never linkifies dangerous URI schemes (`javascript:`, `data:`, `file:`, `vbscript:`). A registered validation step (`note-rendering`, `scripts/check-note-rendering.js`) and the git pre-commit hook scan non-test `.tsx` files for `.notes`/`.sourceNote` fields rendered directly as JSX children (not wrapped in `renderSourceNote(...)`) and fail if any are found. Attribute values, function arguments, method/property access, and conditionals are not flagged. Run `node scripts/check-note-rendering.js` to verify; run `scripts/install-hooks.sh` to (re)install the pre-commit hook.
*   **No External Resources Guard:** KYUTXO is offline-first, so external CDN/script/style/font links must never ship. A registered validation step (`no-external-resources`, `scripts/check-no-external-resources.js`) scans `client/index.html` and the built `dist/public` output (HTML + CSS) for absolute `http(s)://` references in `<link>`/`<script>` tags and CSS `url(...)`/`@import`, failing if any non-allow-listed host is found. The Electron CSP `connect-src` runtime endpoints (`mempool.space`, `blockstream.info`) are allow-listed. Run `node scripts/check-no-external-resources.js` to verify; run `npm run build` first to also scan the production bundle.
*   **Test Provider Harness Guard:** Components that conditionally render an AddressLink/TxidLink throw outside a `RecordPreviewProvider`, and Radix Tooltips throw outside a `TooltipProvider`, so tests must use the shared harness `renderWithProviders`/`TestProviders` (`client/src/test/testProviders.tsx`) rather than a partial/bare provider wrapper. A registered validation step (`test-providers`, `scripts/check-test-providers.js`, also wired into the pre-commit hook) scans `client/src/**/*.test.tsx?` and flags three symmetric missing-provider gaps: (A) a bare `<TooltipProvider>` without a `<RecordPreviewProvider>`, (B) the opposite — a bare `<RecordPreviewProvider>` without a `<TooltipProvider>` (a Tooltip mounted there throws), and (C) a bare `render()` of a known tooltip-capable leaf component (AddressLink, TxidLink, HopPathExplorer, MetadataSourcesPanel, ContinuityProof, BlockchainToggle, ContinuityCertificateReport) with neither provider in the tree. Files using the shared harness are never flagged for B or C. Intentional-mock tests that mock `RecordPreviewContext`/`AddressLink` to assert wiring in isolation (`copy-button-toast.test.tsx`, `copy-button-toast-extra.test.tsx`, `copy-txid-confirmation.test.tsx`, `hover-label-indicator.test.tsx`) are allow-listed via `ALLOWED_FILES` in the script. Run `node scripts/check-test-providers.js` to verify.
*   **No Buffer Global Guard:** The Vite browser bundle does not polyfill the Node `Buffer` global, so any `client/src` code that runs in the browser and uses the `Buffer` global API (`Buffer.from`, `Buffer.alloc`, `Buffer.concat`, `new Buffer(...)`) throws "Buffer is not defined" at runtime — yet passes unit tests because vitest runs in Node where `Buffer` exists (this caused the Proof-of-Funds signature-verification crash). A registered validation step (`no-buffer-global`, `scripts/check-no-buffer-global.js`, also wired into the pre-commit hook) scans non-test `client/src/**` `.ts`/`.tsx` files and fails on any standalone global `Buffer.`/`new Buffer(...)` usage. It blanks comments and strings before scanning (so `Buffer.` inside a comment/string is ignored), and the `(?<![\w$])` lookbehind means identifiers that merely end in `Buffer` (`passwordBuffer`, `hashBuffer`) plus `ArrayBuffer`/`SharedArrayBuffer`/`BufferSource` are never flagged. Use `Uint8Array` end to end (bitcoinjs-lib v7 and `@bitcoinerlab/secp256k1` accept it directly) and `atob`/`btoa` or `base64ToBuffer` in `client/src/lib/crypto.ts` for base64. The opt-in escape hatch is an explicit `import { Buffer } from 'buffer'` (which bundles the polyfill); the test-only helper `client/src/test/pdfAssertions.ts` is allow-listed and `*.test.ts(x)` files are excluded. Run `node scripts/check-no-buffer-global.js` to verify; run `scripts/install-hooks.sh` to (re)install the pre-commit hook.
*   **Proof Verification Browser Guard:** The static no-Buffer scan only checks source text, so it cannot prove the live Vite-bundled crypto path runs Buffer-free. A reusable, browser-safe (Uint8Array + atob/btoa only) self-check `runProofVerificationBrowserCheck` (`client/src/lib/proofVerificationBrowserCheck.ts`) exercises the real `verifyBitcoinSignature` → `verifyBip322P2SH` P2SH-P2WSH BIP-322 path on a valid witness (must verify, `format='bip322'`) plus a tampered witness and a wrong-message proof (must fail cleanly, never silently pass or crash), returning `{ ok, bufferGlobalPresent, steps }`. It runs as two validation steps: `proof-verify-node-check` (Node vitest `proofVerificationBrowserCheck.test.ts` + `signatureVerify.test.ts`, deterministic correctness) and `proof-verify-browser-check` (`node scripts/check-proof-verify-browser.mjs`, the faithful guard) which loads the module in a REAL headless Chromium and fails unless `bufferGlobalPresent === false` AND `ok === true`. Note: faking the browser in Node (`delete globalThis.Buffer`) or jsdom + `resolve.conditions:['browser']` both give false results, because dependency Node builds legitimately use the global `Buffer` and only the real Vite bundle injects the browser polyfills users actually get. The browser runner needs a `chromium` binary on PATH (installed via Nix) and `playwright-core` (no browser download); it reuses the dev server or spawns one. Run `node scripts/check-proof-verify-browser.mjs` to verify.
*   **PDF Glyph Rendering Browser Guard:** Unit tests pin `sanitizePdfText`'s byte mapping (Windows-1252 high-range punctuation — em-dash U+2014→byte 0x97, en-dash, ellipsis, bullet, curly quotes, euro, trademark, dagger — remapped to single WinAnsi bytes for jsPDF's Standard-14 Helvetica) but cannot prove a real PDF viewer paints the glyph instead of a "?" or a UTF-16BE garble. A reusable, browser-safe (Uint8Array only) self-check `runPdfGlyphBrowserCheck` (`client/src/lib/pdfGlyphBrowserCheck.ts`) generates a one-line PDF via the real `sanitizePdfText` path, re-parses it with pdf.js (a real, production-grade PDF engine — the same one Firefox ships), and asserts every remapped glyph round-trips, that no preserved glyph degraded to "?", that no stray high/garble characters appear, and a negative control (an unsupported character → clean "?" while a neighbouring em-dash survives), returning `{ ok, isBrowser, extracted, steps }`. It runs as two validation steps: `pdf-glyph-node-check` (Node vitest `pdfGlyphBrowserCheck.test.ts`, deterministic correctness) and `pdf-glyph-browser-check` (`node scripts/check-pdf-glyph-browser.mjs`, the faithful guard) which loads the module in a REAL headless Chromium and fails unless `isBrowser === true` AND `ok === true`. Notes: pdf.js is only the verification *oracle* (KYUTXO itself never reads PDFs, only writes them with jsPDF), so the check deliberately loads pdf.js's *legacy* build in every environment — the default build (and the Web Worker it spawns) relies on `Promise.try`, which the Nix-pinned test Chromium (v125, pre-Chrome-128) lacks; real users run a modern Electron Chromium that has it, so this is purely a stale-harness-browser gap. Both builds parse the WinAnsi byte stream identically, so the legacy build still faithfully exercises the real Vite-bundled jsPDF generation path. The browser runner needs a `chromium` binary on PATH (installed via Nix) and `playwright-core` (no browser download); it reuses the dev server or spawns one. Run `node scripts/check-pdf-glyph-browser.mjs` to verify.
*   **Sample PDF Browser Guard:** The Proof-of-Funds "Generate Sample PDF" unit tests only capture the strings handed to jsPDF's `doc.text()`, so they cannot prove a real PDF — generated by the live Vite bundle and opened in a real PDF engine — actually paints the diagonal "SPECIMEN" watermark on every page, the red "SAMPLE / SPECIMEN — NOT A VALID DECLARATION" notice banner, or the optional sections (QR, provenance, AML, attestation, glossary) without dropping content. A registered validation step (`sample-pdf-browser-check`, `node scripts/check-sample-pdf-browser.mjs`, mirroring `check-pdf-glyph-browser.mjs`) drives the actual `button-generate-sample-pdf` in a REAL headless Chromium: it creates a fresh vault via the setup form, enables all optional-section switches, clicks the sample button, captures the downloaded blob, and re-parses it with pdf.js's *legacy* build (same flavor/reason as the glyph guard — the Nix test Chromium predates `Promise.try`). It fails unless the recovered text layer shows: page count ≥ 1; "SPECIMEN" on every page; ≥ 2 "SPECIMEN" runs (footer + watermark) on every non-first page (those pages carry no banner, isolating the watermark); the banner text ("SAMPLE" + "NOT A VALID DECLARATION"); the fictitious declarant "Jane Q. Sample"; and NO 64-char hex SHA-256 fingerprint (a specimen must never carry a real fingerprint — sample mode prints a placeholder label instead). The runner needs a `chromium` binary on PATH (installed via Nix) and `playwright-core`; it reuses the dev server or spawns one. Run `node scripts/check-sample-pdf-browser.mjs` to verify.
*   **Dust Badge + Audit Downgrade Browser Guard:** Unit tests cover the dust-flag CRUD (`dust-flags-crud.ts`) and the Privacy Audit downgrade in isolation, but only a real browser proves the three surfaces are wired together: Dusted page "Mark as dust" → UTXOs page Dust badges → Privacy Audit annotated LOW finding. A registered validation step (`dust-badge-audit-browser-check`, `node scripts/check-dust-badge-audit-browser.mjs`, mirroring the other `check-*-browser.mjs` guards) drives a REAL headless Chromium: creates a fresh vault, seeds one owned address + one confirmed transaction with a single unspent 800-sat output via the live Vite module singletons (record-crud/transaction-crud), reloads the Dusted page so the scan picks the seed up on mount, clicks the real `button-mark-dust-*` and waits for it to flip to Unmark (live-query proof the write landed), then asserts the UTXOs group badge ("1 dust") and per-UTXO "Dust" badge (after expanding the group), and finally generates the Privacy Audit and asserts exactly one DUST finding with severity "Low" containing "already marked as dust by you" — and that no non-downgraded (Medium/Critical) unspent-dust finding remains. Fully offline (IndexedDB only, no network). The runner needs a `chromium` binary on PATH (installed via Nix) and `playwright-core`; it reuses the dev server or spawns one. Run `node scripts/check-dust-badge-audit-browser.mjs` to verify.
*   **PDF Text Sanitization Guard:** Every PDF report is drawn with jsPDF's Standard-14 Helvetica, which can only paint WinAnsi (Windows-1252) bytes — any character above 0xFF (em-dash, curly quotes, ellipsis, accented names, emoji) garbles unless routed through `sanitizePdfText(...)` (`client/src/lib/pdfText.ts`), which the `pdf-glyph-*` guards already prove renders correctly. A static guard (`pdf-text-sanitized`, `scripts/check-pdf-text-sanitized.js`, also wired into the pre-commit hook and `scripts/install-hooks.sh`, mirroring `check-no-buffer-global.js`) scans non-test `client/src` files that contain `new jsPDF` and flags two classes of jsPDF text sinks — `doc.text(...)`/`doc.cell(...)` and `autoTable` `head`/`body` cells — whose first argument is not wrapped in `sanitizePdfText(...)`. It strips comments, builds a per-file variable map (single-assignment `const`/`let`/`var`, `for...of` loop vars, and function/arrow params resolved through their call sites) and transitively inlines those single-assignment values so upstream literals/members surface; scope-bound names (callback params like `m` in `.map((m) => …)`, loop vars) are never inlined, so they cannot collide with a same-named file-level binding. Check A (all sinks) fails on a non-ASCII character that is not inside a `sanitizePdfText(...)` call; Check B (`doc.text`/`doc.cell` only) fails on a bare lowercase member expression (e.g. `record.note`) that reaches jsPDF unwrapped — pure-ASCII string literals, ternary conditions, and SCREAMING_SNAKE_CASE constant roots are treated as safe. Known limitations: runtime `${userVar}` template interpolations are not taint-checked, and non-ASCII inside imported constant modules (which lack `new jsPDF`) is not scanned. The escape hatch for a genuine false positive is adding `"file:line"` to `ALLOWED_LINES` in the script. Run `node scripts/check-pdf-text-sanitized.js` to verify; run `scripts/install-hooks.sh` to (re)install the pre-commit hook.
