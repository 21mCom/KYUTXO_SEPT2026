# Demo Showcase Vault

A curated, restorable demo database built from **real on-chain data** (every
txid and address exists on Bitcoin mainnet) with fictional persona metadata,
so every major KYUTXO feature shows compelling results in a live demo.

## Files

| File | Purpose |
|---|---|
| `demo/kyutxo-demo-vault.zip` | Standard v3 backup (plaintext). One-click load: on a **fresh (empty) vault**, the Records page empty state shows a **Load demo vault** button — pick this zip and the full demo restores in one step. Or restore via **Settings → Backup & Restore → Restore from file** into any vault. The zip is intentionally not bundled into the app. |
| `demo/demo-entity-list.json` | Importable entity-list snapshot (12 fictional attributions on real hub addresses). **Auto-applied on restore** (rides in the backup's portable settings, merge mode) — the standalone file is only needed if you want to re-import it manually. |
| `demo/coverage-report.json` | Machine-written coverage matrix + presenter highlights (persona → addresses, standout txids). Regenerated by the builder. |
| `scripts/demo-vault/build-demo-vault.mjs` | Builder: scans mempool.space / blockstream.info Esplora APIs (rate-limited, disk-cached under `scripts/demo-vault/cache/`, fully resumable), curates the dataset, writes the three files above. Run via the `demo-vault-build` workflow. |
| `scripts/check-demo-vault-restore-browser.mjs` | Real-browser verification: restores the zip into a fresh vault in headless Chromium and walks the coverage matrix (13 checks) including a full Privacy Audit run. |

Scale: ~4,500 address records + ~700 transactions (~5,200 combined, in the
5k–10k target) with ~30,000 participant rows, ~700 lineage edges and ~60
custody segments. History spans **~12 years** of real activity. Restore takes
~40 s; the Privacy Audit over the whole vault finishes in ~15 s.

> Numbers and example addresses below match the committed zip. If you re-run
> the builder the curation is re-derived — always take fresh examples from
> `demo/coverage-report.json` → `highlights`.

## Storyline & personas

All addresses are real; the people are fiction. The "owned" subset (30
addresses, curated tiers via `addressImportance`) was adopted from real
counterparties of bundled entity-list addresses — so direct entity contact is
true on-chain history, not staging.

| Persona | Wallet / seed | Story | Tier |
|---|---|---|---|
| **Avery Stone** | Glacier Cold Storage / Glacier Seed (Sparrow) | Long-term holder; keeps a legacy P2PKH with an exposed pubkey (quantum-risk talking point) and caught a dusting incident. | `verified` |
| **Blake Rivera** | Trading Hot Wallet / Hot Wallet Seed (Electrum) | Active trader; most addresses touch exchange / gambling / mixer-adjacent counterparties. Acquisition method: exchange-purchase. | `wallet-import` |
| **Casey Mora** | Shop Register / Shop Seed (BTCPay Server) | Merchant income; reused payment addresses. | `manual` |
| **Dana & Eli Family Trust** | Meridian Vault 2-of-3 (Sparrow) | 2-of-3 multisig vault; P2SH/P2WSH addresses grouped under `vault` metadata. | `xpub-derived` |

Everything else is `blockchain-discovered`: entity-list counterparties keep
their real attribution (e.g. "Binance (exchange)"), plain counterparties are
labeled "Observed counterparty #n" — no unlabeled rows anywhere.

## Feature walkthrough (suggested order)

1. **Balance / Vaults** — holdings across the four owners; the Meridian Vault
   2-of-3 grouping (7 vault records). Curated rows carry precomputed stats
   caches, so surfaces render instantly.
2. **Records / Transactions / UTXOs** — ~4.5k labeled records, 12 years of
   real history, real fees/heights/weights and wallet-fingerprint fields
   (RBF, BIP-69, witness mix) on every transaction.
3. **Address Reuse** — `197LQ2fD8oXvr5nzwetZLNj7atX76qy9Ta` (Blake): 64
   receipts on one address.
4. **Dusted** — `14f82ZcYBfgsj9j6pd8ps1Gt5XvRM7tZsa` (Avery, "Dusted deposit
   address") received a 1,000-sat output in tx `7809e54e…325e44`.
5. **Quantum Risk** — the same Avery P2PKH has spent (pubkey exposed on
   chain).
6. **Privacy Audit + Adversary Screening** — run the audit: entity findings in
   four categories (exchange, mixer, scam, darknet) from 41 direct-contact
   transactions, plus the merged demo snapshot ("Demo OTC Desk", "Demo Mixing
   Service", "Demo HYIP Collector") for extra hits; proximity findings come
   from the hop-2 counterparty histories included in the dataset. 300+ owned
   co-spend transactions drive adversary clustering vs ground truth.
7. **Fund Trail / Provenance** — start from a Blake address such as
   `1KsCB7H72C3CYCEenBpuMe5BRBMDuHta6g`; custody segments walk real spend
   chains (see `highlights.deepSegments` for txid chains), lineage edges cover
   owned inflows/outflows across months.
8. **Lightning Speculator** — P2WSH (channel-like) outputs are present.
9. **Reports / Proof of Funds / Statements** — generate against Avery or the
   Family Trust: owners, wallets, acquisition methods and custody narratives
   are all populated, so documents come out with meaningful content.

## Rebuilding the dataset

```
# resumable; every HTTP GET is cached under scripts/demo-vault/cache/
Run the "demo-vault-build" workflow   (node scripts/demo-vault/build-demo-vault.mjs)

# verify in a real browser (13-step coverage matrix + live Privacy Audit)
node scripts/check-demo-vault-restore-browser.mjs
```

The builder exits non-zero and prints `COVERAGE GAPS` if any matrix pattern
(dust, reuse, exposed-pubkey P2PKH, entity contact, vault grouping, time
span, totals range…) is not satisfied; gap-fill passes adopt additional real
addresses until it is.

Curation guardrails baked into the builder:

- All txids/addresses are fetched from public Esplora APIs — nothing is
  synthesized; only labels/owners/tags are fictional and say so in notes.
- Only curated-tier records get `walletName` + cached stats; discovered
  counterparty rows never do (keeps balance surfaces truthful).
- The demo entity snapshot is delivered through the existing user-snapshot
  import mechanism (settings `entityListSnapshot`, merge mode) — the bundled
  entity list is untouched.
